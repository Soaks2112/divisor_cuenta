# Divisor de Cuenta Constitution

## Core Principles

### I. SOLID (NON-NEGOTIABLE)

The code MUST respect SOLID. SRP requires one class to have one reason to change:
calculation MUST NOT validate or format. OCP requires that adding a rounding rule MUST
NOT require editing existing calculation classes. LSP requires every implementation of an
interface to substitute for another without type checks by its caller. ISP requires small
interfaces so consumers do not depend on unused methods. DIP requires presentation to
depend on domain abstractions and never on concrete data classes.

### II. Layered Architecture

The application MUST use `presentation`, `domain`, and `data` layers. Dependencies MUST
follow `presentation -> domain <- data`. The `lib/domain/` directory MUST NOT import
`package:flutter` and MUST remain pure Dart. `main.dart` MUST be the only place where
concrete implementations are instantiated.

### III. Secure Local Operation

The application MUST work without network access, external services, or a database for
the account-splitting MVP. The repository MUST NOT contain secrets, API keys, credentials,
or other private tokens. Any future external integration MUST be explicitly specified
before implementation.

### IV. Testable Quality

Every critical calculation and validation rule MUST have an automated test. Every
acceptance criterion in a feature specification MUST become an executable test. Domain
tests MUST run without Flutter widgets. A change is complete only when its relevant tests
and `flutter analyze` pass.

### V. Student Explainability

Every function generated by the agent MUST be explainable by the student: what it does,
why it exists, what it receives, what it returns, and what errors it produces. Names MUST
be in Spanish, null safety MUST be enabled, and external packages MUST NOT be added unless
the student explicitly requests and understands the dependency.

## Architecture and Security

The MVP is a single-screen Flutter application for dividing a restaurant bill. It accepts
the total amount, number of people, and tip percentage, then displays the amount per
person. State may remain local to the screen. Android and iOS platform files MUST NOT be
modified unless a requirement explicitly depends on them. The `test/` directory MUST NOT
be changed without an explicit testing request. The `pubspec.yaml` MUST NOT gain a new
dependency without prior notice.

## Quality, Testing, and Workflow

The required verification commands are `flutter pub get`, `flutter run`, `flutter
analyze`, and `flutter test`. Before implementation, the feature specification, plan, and
tasks MUST be consistent with this constitution. Reviews MUST check layer dependencies,
domain independence from Flutter, concrete-instantiation boundaries, executable acceptance
tests, and the absence of secrets. When a rule fails, the responsible Spec Kit artifact
MUST be corrected before patching code that only hides the violation.

## Governance

This constitution governs all project code and overrides informal implementation habits.
Amendments MUST document the changed principle or section, the reason, and the expected
impact on existing artifacts and tests. The constitution version follows semantic
versioning: MAJOR for incompatible removals or reinterpretations, MINOR for new or
materially expanded principles, and PATCH for clarifications or wording corrections.

Every feature plan and implementation review MUST verify compliance with this document.
Any justified exception MUST be written in the relevant plan and accepted before
implementation. The constitution MUST be reviewed whenever the architecture, testing
strategy, dependency policy, or security requirements change.
